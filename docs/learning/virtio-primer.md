## 1. Общая картина — host, VMM, guest

```
ТВОЙ НОУТ (host machine)
│
├── host kernel (Linux на твоём ноуте)
│     управляет РЕАЛЬНЫМ железом: твоим диском, твоей сетью
│
├── host-процессы
│     bash, VS Code, Firefox-на-ноуте
│
└── rust-nano-vm   (тоже просто host-процесс)
     │ открывает /dev/kvm, просит host kernel создать VM
     │
     └── VM (виртуальная машина)
          │
          ├── guest kernel   ← ВТОРОЙ, отдельный Linux
          │     ДУМАЕТ что у него своё железо
          │     его железо = ЭМУЛЯЦИЯ host-ом
          │
          └── guest-процессы
                Firefox-внутри-VM, Spring Boot, bash
                запускаются guest kernel-ом, не host-ом
```

**Ключевые роли:**

- **Host kernel** управляет РЕАЛЬНЫМ железом (сетевой картой ноута,
  диском).
- **rust-nano-vm** — обычный host-процесс. Через `/dev/kvm` просит
  host kernel создать VM.
- **Guest kernel** — ВТОРОЙ, отдельный Linux внутри VM. Думает что у
  него своё железо.
- **Guest-процессы** (Firefox, Spring Boot, bash) — запускаются
  guest kernel-ом так же как любой Linux запускает процессы.

**KVM — очень узкая штука.** Делает только:

- Запускает guest-овский код на реальном CPU **безопасно и быстро**
  (через аппаратную фичу Intel VT-x / AMD-V).
- Перехватывает **конкретные события**: обращения к не-RAM адресам
  (MMIO), особые инструкции (`hlt`, `cpuid`, I/O ports).
- Будит userspace (`rust-nano-vm`), сообщает что guest сделал.
- Делает аппаратный перевод GPA → HPA (Extended Page Tables).

KVM **НЕ** эмулирует устройства, НЕ грузит ядро, НЕ знает про сеть/диск.
Всё это — работа `rust-nano-vm`.

**Разделение ролей:**

```
Реальный компьютер:  [CPU] + [чипсет + устройства] + [ОС]
                       │             │                │
VM:                   [KVM] + [rust-nano-vm] + [guest OS]
```

- KVM играет роль **CPU + MMU**.
- rust-nano-vm играет роль **"всей остальной материнки"** — чипсет,
  шины, устройства, BIOS, boot logic.
- Guest OS — пилот в кабине.

**Firecracker, QEMU, Cloud Hypervisor, rust-nano-vm — аналоги друг
друга.** Все используют KVM снизу, но делают разный набор устройств
и режим boot-а.

## 2. Kernel vs userspace

Когда Java-код пишет `new FileInputStream("data.txt")` и читает
байты — **ты не разговариваешь с диском напрямую**. Между:

```
   Твой Java-код        (user space)
        │ вызов API
        ▼
       JVM
        │ системный вызов (syscall)
        ▼
   Ядро Linux            (kernel space)
        │ команды контроллеру диска
        ▼
   Hardware              (сам диск)
```

**Ядро (kernel)** — специальная программа:

- Единственная может напрямую трогать железо (диск, сеть, память,
  устройства).
- Пускает к себе приложения только через **syscall** (`read`,
  `write`, `open`).
- Защищает одно приложение от другого — у каждого свой кусок памяти.

**Приложение (user space)** — Firefox, Java-прога, bash. **Не
могут** писать на диск напрямую. Только просят ядро "положи вот
эти байты в файл".

Это разделение — основа всех современных ОС. Иначе любое
приложение могло бы стереть чужие файлы или сломать железо.

## 3. Что такое "устройство"

**Устройство (device)** = всё что НЕ CPU и НЕ RAM. Диск, сетевая
карта, клавиатура, GPU, часы, флешка.

### На реальном железе

Общаются через **чтение/запись в специальные адреса памяти**, которые
на аппаратном уровне подключены не к RAM, а к устройству.
Это называется **MMIO (Memory-Mapped I/O)**.

Пример: записать в адрес `0xFEC00000` байт `0x01` — и сетевая карта
понимает это как "начать передачу". Железо так спроектировано:
процессор думает что пишет в память, а провода уходят в чип
сетевой карты.

### MMIO-регистры назначаются через PCI

На реальной материнке есть **PCI bus** — многоконтактный разъём, к
которому подключены устройства. Что происходит при включении:

1. **BIOS/UEFI** проходит по шине, спрашивает каждое устройство:
   "кто ты? сколько тебе надо памяти под регистры?". У каждого
   устройства есть **конфигурационное пространство** (vendor ID,
   device ID, нужный диапазон).
2. BIOS **назначает** устройству диапазон: "сетевая карта в слоте
   3 — твой MMIO `0xFEC00000..0xFEC00FFF`", записывает этот адрес
   обратно в конфиг-регистр устройства.
3. **Чипсет мамки** знает: "записи процессора в `0xFEC00000..` —
   маршрутизировать на сетевую карту". Физически провода +
   программируемый роутер в чипсете.
4. **Ядро** при загрузке читает PCI-конфигурации и узнаёт: "в
   этом слоте — сетевая карта с MMIO `0xFEC00000`". Грузит
   соответствующий драйвер.

**"Инициализировать устройство"** = ядро проходится по регистрам,
ведёт диалог: "ты какое? какие у тебя возможности? вот адрес,
куда тебе класть данные". Без этого устройство не знает с кем
работать.

### В VM

PCI физически нет. `rust-nano-vm` **играет в неё**:

- В коде есть примерно так:
  ```rust
  let virtio_net = VirtioNetDevice::new();
  pci_bus.attach(virtio_net, slot = 3);
  ```
- **"Устройство" — это буквально Rust-структура** с методами
  `read(offset)` и `write(offset, value)`. В ней ID, диапазон
  MMIO-адресов, внутреннее состояние.
- **PCI-шина** — тоже Rust-структура. Когда guest опрашивает её
  через стандартные PCI-порты, сработает VM-exit, rust-nano-vm
  ответит "в slot 3 висит virtio-net 0x1AF4/0x1000".

## 4. Как устройство появляется в VM

### Фаза A — host готовит симулятор (ДО старта guest-а)

Guest ещё НЕ запущен. `rust-nano-vm` исполняет код:

1. `ioctl(KVM_CREATE_VM)` — создаёт пустую VM. "Коробка симулятора".
2. `mmap()` 128 MB памяти → `ioctl(KVM_SET_USER_MEMORY_REGION)` —
   говорит KVM "эта память = guest-овская RAM".
3. Загружает образ ядра (`bzImage`) в выделенную RAM, в адрес
   `0x100000`.
4. **Создаёт виртуальные устройства** — Rust-structs. Регистрирует
   MMIO-диапазоны этих устройств.
5. Настраивает перехват: "когда guest обращается к MMIO —
   генерируй VM-exit, буди меня".
6. `ioctl(KVM_RUN)` — запускает vCPU. **Guest стартует.**

### Фаза B — guest загружается и находит устройство

Guest kernel стартовал. Не знает что в VM. Делает ровно то же что
на реальном железе:

1. **Опрашивает PCI-шину**: "эй, кто на тебе висит?"
   Шина виртуальная — Rust-struct внутри rust-nano-vm. Guest,
   обращаясь к стандартным PCI-портам, вызывает VM-exit.
   rust-nano-vm отвечает: "в slot 3 — vendor=0x1AF4
   device=0x1000". Это тот VirtioNetDevice, которого rust-nano-vm
   **создал на шаге 4 фазы A**.
2. **Узнаёт**: 0x1AF4/0x1000 = virtio-net. Ищет в своих модулях
   драйвер.
   **Где драйвер?** В самом ядре Linux. Linux компилируется с
   тысячами драйверов внутри. `virtio_net.ko` — один из них.
   Guest грузит этот модуль из своего образа ядра. Это
   **стандартный Linux-овский код, он на любом Linux есть**.
3. **Драйвер инициализирует устройство** через MMIO:
   - Выделяет память в guest-RAM под descriptor table
   - Пишет её GPA в MMIO-регистр virtio-net ("queue descriptor
     address")
   - rust-nano-vm перехватывает запись, запоминает где лежит
     таблица
4. **Linux регистрирует `eth0`**. Готов отправлять пакеты.

### Три важных факта

**Факт 1.** Устройство — **Rust-структура в памяти host-процесса**.
Существует потому что rust-nano-vm явно создал этот объект в своём
коде.

**Факт 2.** **Guest ничего не создаёт — он только находит.** Guest
kernel использует стандартную процедуру опроса PCI, одну для
реального железа и для VM.

**Факт 3.** **Драйвер (virtio-net.ko) уже есть в guest-овской
Linux.** Это стандартный open-source Linux-код. Host никакого
драйвера в guest не загружает — только выставляет устройство с
правильным vendor/device ID.

## 5. MMIO: регионы, VM-exit, маршрутизация

### Как "помечается" MMIO в VM

**Негативно.** Ты НЕ говоришь KVM "вот эти адреса — MMIO". Ты
говоришь: "вот эти — RAM". Всё остальное автоматически становится
MMIO.

```rust
kvm_set_user_memory_region(vm, &MemorySlot {
    guest_phys_addr: 0,                     // с GPA 0
    memory_size: 128 * 1024 * 1024,         // 128 MB
    userspace_addr: guest_ram_base,         // host-овский HVA
});
```

Это говорит KVM: "GPA 0..128MB — настоящая RAM, backing-ана по
моему HVA `guest_ram_base`". rust-nano-vm **НЕ регистрирует**
диапазон `0xFEC00000..`. Пропускает его. **Этого достаточно.**

### Что происходит при обращении guest-а

1. Guest пишет в `0xFEC00000`.
2. CPU смотрит в Extended Page Tables (EPT — аппаратная таблица
   второго уровня): "есть mapping для 0xFEC00000?" → **нет**.
3. Hardware генерирует **EPT violation = VM-exit**.
4. KVM в host-кернеле просыпается, смотрит: "этот диапазон не был
   зарегистрирован как RAM, значит MMIO". Будит `rust-nano-vm`:
   "guest хотел писать `V` в `0xFEC00000`, что делать?"
5. `rust-nano-vm` смотрит в **свою внутреннюю таблицу устройств**:
   ```rust
   for device in &devices {
       if device.contains(gpa) {
           return device.handle(gpa - device.base, is_write, value);
       }
   }
   ```
6. Вызывает `virtio_net.write(offset=0, value=V)`. Что-то меняет
   в своих Rust-полях. Говорит KVM "обработал, продолжай".
7. KVM возобновляет исполнение guest-а.

### Два уровня "пометки"

- **KVM-уровень**: "RAM / не RAM" (бинарно). Единственная цель —
  вызвать VM-exit.
- **VMM-уровень** (rust-nano-vm): "не-RAM GPA → какое устройство".
  Это маршрутизация.

### Java-аналогия для MMIO-регистра

Это как **Spring-овский `@RequestMapping("/foo")`**. С точки зрения
клиента `/foo` — это "адрес", к которому он обращается. Spring
перехватывает запрос и вызывает соответствующий Java-метод.
MMIO-регистр = тот же "эндпоинт", только адрес числовой, а
перехватчик — KVM + rust-nano-vm.

## 6. Память: GPA, HVA, два взгляда

На современных CPU есть **MMU (Memory Management Unit)** —
аппаратный переводчик адресов.

- **HVA (Host Virtual Address)** — виртуальный адрес в
  адресном пространстве host-процесса (rust-nano-vm). На x86_64 —
  48-битный. Пример: `0x7f2000_001000`.
- **GPA (Guest Physical Address)** — "физический" адрес с точки
  зрения guest-а. **Ложь** — это не настоящий физический. Пример:
  `0x40001000`.
- **HPA (Host Physical Address)** — настоящий физический адрес
  RAM-чипа.

### Цепочка

    Guest виртуальный адрес
        ↓ guest-овские page tables (управляет guest kernel)
    Guest физический адрес (GPA)
        ↓ EPT/NPT (настраивает KVM, использует CPU)
    Реальная RAM (HPA)

    Отдельный путь для доступа VMM к той же RAM:
    Host виртуальный адрес (HVA)
        ↓ host-овские page tables (управляет host kernel)
    Та же RAM (HPA)

При исполнении guest-а CPU переводит GPA напрямую в HPA через EPT/NPT.
HVA — отдельный view host-процесса на те же backing pages, а не
промежуточный этап аппаратного перевода guest-адреса.

### Один физический байт, два view

```
Один физический байт RAM-а на твоём ноуте
    ↑ видят оба:                    ↑
guest видит его как                  host (rust-nano-vm) видит его
GPA 0x40001000                       как HVA 0x7f2000_001000
```

### Для rust-nano-vm перевод GPA → HVA — сложение

Когда rust-nano-vm создавал guest-RAM:
```rust
let guest_ram_base: *mut u8 = unsafe {
    libc::mmap(null_mut(), 128 * 1024 * 1024, ...)
};
// Linux вернул кусок памяти, начиная с какого-то HVA,
// например 0x7f2000_000000. Это АРБИТРАРНЫЙ адрес —
// Linux выбрал где-то в свободном месте твоего адресного
// пространства.
// Запоминаем guest_ram_base = 0x7f2000_000000.
```

Потом говорит KVM:
```rust
kvm_set_user_memory_region(vm, &MemorySlot {
    guest_phys_addr: 0,             // с GPA 0 в госте
    memory_size: 128 * 1024 * 1024,
    userspace_addr: guest_ram_base, // соответствует HVA
});
```

**Перевод = сложение**:
```rust
fn gpa_to_hva(gpa: u64) -> *const u8 {
    unsafe { guest_ram_base.add(gpa as usize) }
}

// guest_ram_base = 0x7f2000_000000
// gpa            = 0x40001000
// HVA            = 0x7f2000_000000 + 0x40001000
//                = 0x7f2040_001000
```

Если ты в Java когда-нибудь работал с `ByteBuffer` и offset-ами —
та же логика.

## 7. VirtIO — протокол producer-consumer

### Задача

Guest и host не могут звать функции друг у друга — разные
privilege levels. Каждый "крик через стену" (vmexit) стоит тысячи
тактов. Нужен способ:

1. Общаться через **общую память** (не syscall-ы).
2. **Батчить** — guest кидает 10 пакетов, потом сигналит один раз.
3. **Асинхронно** — guest не блокируется.
4. **Lock-free** — никаких мьютексов (vmexit дорог).

Это **классический producer-consumer**. Если ты это делал в Java —
`BlockingQueue`, Disruptor, `kfifo`. **Virtqueue — конкретная
реализация**, оптимизированная под эти 4 требования.

### Структура, в 4 шага построения

**Ступень 1 — самый тупой вариант.** Одна переменная в shared
memory:
```c
u64 packet_addr;   // "вот тут лежит пакет"
bool has_work;     // "guest положил работу"
```

Проблема: только ОДИН пакет за раз. Batching невозможен.

**Ступень 2 — массив вместо одной переменной.** Здесь рождается
монотонный `idx`:
```c
u64 packet_addrs[128];
u32 next_free_slot;  // guest-ный счётчик
```
Guest кладёт адрес в `packet_addrs[next_free_slot]`, инкрементит.
Host хранит у себя `last_seen = 0`. Читает `next_free_slot` →
обработал, поднял `last_seen`.

**Это и есть `idx` counter из спеки.** Не "зачем-то счётчик" —
**единственный способ** host-у узнать "какие записи новые", не
порождая дополнительной shared-переменной, которую опять надо
синхронизировать.

**Ступень 3 — packet это не просто адрес. Рождается descriptor
table.** Пакет = адрес + длина + направление + возможно chain
(размазан на несколько страниц для scatter-gather). Значит:

```rust
struct Descriptor {
    addr:  u64,
    len:   u32,
    flags: u16,   // WRITE / NEXT (chained) / ...
    next:  u16,   // следующий слот цепочки, если flags & NEXT
}
```

Можно было бы инлайнить структуру прямо в ring. Но пакет из 3
кусков = **одна** работа в ring-е, **три** дескриптора. Поэтому
разделяют:

- **Descriptor table** — пул слотов (= чердак с подносами). 128
  слотов, переиспользуются, нумерованы.
- **Ring** — последовательность НОМЕРОВ слотов, в порядке обработки.

Chain: guest кладёт 3 дескриптора в слоты #5, #12, #0. В #5:
`flags = NEXT, next = 12`. В #12: `flags = NEXT, next = 0`. В #0:
`flags = 0`. А в ring кладёт **только номер головы = 5**. Host
читает ring[idx] = 5 → идёт в descriptor_table[5] → видит NEXT →
идёт в [12] → NEXT → в [0] → конец.

**Три буфера, один логический пакет, одна запись в ринге.**

**Ступень 4 — ВТОРОЙ ринг. Рождается lock-free.**

Сейчас один ring — "available", guest говорит host-у "обработай
эти". Как host скажет "готово"?

- Вариант A — писать обратно в тот же ring → race, нужен lock →
  **ломает lock-free**.
- Вариант B — ВТОРОЙ ring, "used":
  - **Available ring**: только guest пишет, только host читает.
  - **Used ring**: только host пишет, только guest читает.
  - Single-writer single-reader → **no lock**.

**Два ринга — не прихоть автора, а прямое следствие требования
lock-free.**

### Итого — почему каждая штука

| Элемент | Что решает |
|---|---|
| **Монотонный `idx`** | "Где новые записи?" без доп. shared state |
| **Descriptor table** (отдельный пул) | Zero-copy (адреса, не копии) + chain для scatter-gather |
| **Два ринга** (avail + used) | Lock-free (один писатель на ячейку) |

Каждая штука = **прямое следствие** одного из 4 требований, не
случайная усложнёнка.

### Handshake — как host узнаёт где лежит descriptor table

1. Guest kernel находит virtio-net через PCI.
2. Guest kernel **выделяет** 3 куска памяти в своей RAM
   (descriptor table, avail ring, used ring).
3. Guest kernel **пишет GPA этих областей в MMIO-регистры**
   устройства ("queue descriptor address", "queue avail address",
   "queue used address" — стандартные поля virtio spec).
4. **Host (rust-nano-vm) перехватывает** эти записи через
   VM-exit, запоминает GPA-адреса.

**С этого момента оба знают.** Guest пишет descriptor-ы в свою
память по GPA. Host переводит GPA → HVA через `guest_ram_base +
gpa`, читает/пишет ту же память через свой view.

**Кто выбирает адреса — guest.** Host — пассивный регистратор.

### Размер descriptor table

Обычно **128 или 256 слотов**. Спека разрешает любую степень
двойки до 32768. Это просто **выбор разработчика device-side кода**
(host). 128 — компромисс: достаточно для батчинга, не разбухает.

## 8. Что нужно Java (devices wise)

JVM напрямую про устройства не знает — трогает Linux под собой.
Spring Boot минимально требует:

| Устройство | Зачем | Что при его отсутствии |
|---|---|---|
| **Serial port (console)** | `System.out.println`, логи boot-а | JVM стартует молча; не увидишь stack trace |
| **Timer** (PIT/HPET или виртуальный) | `currentTimeMillis`, `Thread.sleep`, GC pauses, scheduler | Linux вообще не загрузится |
| **Interrupt controller (APIC)** | Прерывания от других устройств | MMIO-notify не работает, guest не получит ответ |
| **virtio-net** | Spring Boot HTTP server, JDBC, микросервисы | `Connection refused` на любую сеть |
| **virtio-blk / virtio-fs** | Classpath (JAR-ы), конфиг-файлы, JIT-кеш | `ClassNotFoundException` |
| **virtio-vsock** | Control-plane host↔guest ("start", "ready") | Host не узнает что guest готов |
| **virtio-rng** | TLS, `SecureRandom`, UUIDs | **Spring Boot зависает 30+ сек** ждя `/dev/random` |

**7 устройств — минимум для Spring Boot.** Не "архитектурное
излишество", а **требование рабочей ОС + типичного Java-приложения**.

## 9. vqparse — твоё место в картине

**VirtIO — это не программа, а протокол. Спецификация ФОРМАТА БАЙТ.**

Спека говорит: "в descriptor table лежат 16-байтные записи вида
`{addr: u64, len: u32, flags: u16, next: u16}`, little-endian".

Чтобы с этими байтами работать — **нужен код, который их
декодирует**:

- Берёт 16 сырых байт из памяти.
- Распознаёт: байты 0..8 = `addr`, 8..12 = `len`, 12..14 = `flags`,
  14..16 = `next`.
- Учитывает endianness.
- Валидирует (`next` не больше размера таблицы? `flags` — известные
  биты?).
- Умеет пройти по цепочке `next`.

Это и есть **парсер**.

### Аналогия, которую ты каждый день видишь

**JSON** — тоже протокол ("ключ-значение в фигурных скобках"). Когда
ты в Java пишешь:
```java
new ObjectMapper().readValue(json, User.class)
```
ты зовёшь **парсер JSON**. Он превращает строку `{"name":"Igor"}`
в типизированный Java-объект `User`.

**Без парсера у тебя просто массив char-ов, с которым ничего не
сделать.**

**vqparse = парсер VirtIO.** Превращает 16 байт из guest-памяти в
типизированный Rust-struct `Descriptor`, с которым остальной код
rust-nano-vm может работать:

```rust
let bytes: [u8; 16] = /* сырые байты из guest-памяти */;
let descriptor: Descriptor = vqparse::decode(&bytes)?;

// теперь можно удобно:
descriptor.addr    // u64
descriptor.len     // u32
descriptor.flags   // bitflags
descriptor.next    // u16
```

### Типичная функция vqparse

```rust
pub fn decode_descriptor(bytes: &[u8; 16]) -> Result<Descriptor, Error> {
    // little-endian decoding
    let addr  = u64::from_le_bytes(bytes[0..8].try_into().unwrap());
    let len   = u32::from_le_bytes(bytes[8..12].try_into().unwrap());
    let flags = u16::from_le_bytes(bytes[12..14].try_into().unwrap());
    let next  = u16::from_le_bytes(bytes[14..16].try_into().unwrap());
    Ok(Descriptor { addr, len, flags, next })
}
```

**Это ВСЯ суть парсера.** Остальное — валидация, chain-прохождение,
обработка ошибок, тесты.

### Scope vqparse

- **no_std** — работает без OS, пригоден даже для guest kernel-а.
- **Pure** — чистые функции байты → структуры, без I/O, без
  аллокаций.
- **Тестируемо** — на реальных байтах из реальной VirtIO-трассировки
  (можно записать bytes в тестовую фикстуру).
- **Не реализовывать всю машинерию producer-consumer** — тебе надо
  уметь только читать байты и декодировать их. Все `handshake`,
  `VM-exit`, `shared memory` — не твоя область.

## 10. Аналогии

### Flight simulator (системный уровень)

| В симуляторе | В VM |
|---|---|
| Пилот | **Guest kernel** |
| Кабина с приборами | "Железо" которое видит guest |
| Отдельный прибор (рычаг, экран) | **Устройство** (virtio-net, таймер) |
| Компьютер симулятора | **rust-nano-vm** |
| Оператор настраивает кабину ДО сеанса | rust-nano-vm создаёт устройства ДО старта guest-а |
| Сигнал от рычага → компьютер | **VM-exit**: guest трогает регистр — управление в rust-nano-vm |

### Restaurant kitchen (VirtIO protocol уровень)

- **Клиент** = guest.
- **Повар** = host.
- **Стойка между ними** = shared memory.
- **Подносы с номерами 0..127** = descriptor table.
- **Клипборд "заказал"** = available ring.
- **Клипборд "готово"** = used ring.
- **Колокольчик** = MMIO notify-регистр (вызывает VM-exit).

**Поток:**
1. Клиент кладёт еду на поднос #5 (= буфер в guest-памяти, адрес
   записан в `descriptor_table[5]`).
2. Пишет `5` на клипборд "заказал".
3. Звонит в колокольчик.
4. Повар видит `5` → забирает поднос → готовит → возвращает.
5. Пишет `5` на клипборд "готово", звонит в свой колокольчик.
6. Клиент знает что поднос #5 свободен.

## 11. Архитектурный контекст (x86 vs ARM, AI-датацентры)

### Текущий фокус rust-nano-vm

- **v1**: Linux + KVM на **x86_64** (Intel VT-x, AMD-V). Основной
  enterprise-таргет: Spring Boot.
- **v2**: ARM64 (aarch64). KVM есть на ARM, VirtIO — архитектурно
  независим. Это **инженерный порт**, не переписывание.

### AI-датацентры не делают эту технологию устаревшей

Миф: "дата-центры уходят с Intel". Реальность сложнее:

- **GPU-серверы всё равно имеют x86 (или ARM) CPU** в качестве
  host-а. NVIDIA H100/H200 — ускоритель, не замена CPU. Типично:
  2× AMD EPYC + 8× H100. CPU управляет оркестрацией, GPU делает
  linear algebra.
- **ARM64 растёт**: AWS Graviton (3-4 поколение), NVIDIA Grace,
  Azure Cobalt, Google Axion. Но ARM — альтернатива x86, не
  альтернатива виртуализации. KVM+VirtIO работают на ARM
  одинаково.
- **Специализированные AI-чипы** (TPU, Trainium) — не
  general-purpose CPU. На них **не запустить Spring Boot**.

### Что это значит для vqparse

- Твой парсер **не привязан к архитектуре**. Работает на x86, ARM,
  любой платформе где есть Rust.
- Логика "битовый формат → типизированные structs" — универсальная.
- Знания из VirtIO спеки — применимы в любом hypervisor-е
  (Firecracker, QEMU, rust-nano-vm, твой собственный).
